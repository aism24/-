# 入熱・パス間温度管理アプリ

鉄骨溶接の**入熱・パス間温度管理**を、現場でiPad/スマホから簡易入力し、履歴を蓄積してPDFで出力できるアプリです。
リポジトリ直下の「試合記録アプリ」と同じ構成（**GitHub Pagesでフロントエンド配信 + Google Apps ScriptでJSON API + スプレッドシート/Driveをデータストア**）を採用しています。

## データ構造(1行=1パスのフラット表)

このアプリは「工事/部材/継手/パス」を別シートに分けず、**1行=1パスのフラットなスプレッドシート**に記録します。
1つの継手(一連の溶接)を記録すると、パスの数だけ行が一括で追加され、各行に工事名・部材・製品名などのヘッダー情報が重複して書き込まれます。

「同じ継手のパスかどうか」は、**「順序」列が1に戻った行を新しい継手の開始とみなす**ルールで判定します(このアプリは1継手分のパスを必ずまとめて連続した行として書き込むため、この判定で正しく区別できます)。

流れ: 「継手情報を入力 → パスごとにスタート/ストップで計測しながら記録 → (任意で)積層図(鋼材に描かれた図)を撮影 → 溶接完了ボタンでスプレッドシートへ一括保存 → PDF出力」

継手情報入力画面の「サイズ(幅)・板厚・部材サイズ・溶接長・気温・計測・入熱上限・パス間温度下限/上限・ルートギャップ・開先角度」は、前回記録した継手(スプレッドシート最終行)の値がデフォルト表示されます(「製品名」はOCRで都度読み取る製品固有のタグ情報のため対象外です)。同様に、1パス目の電流・電圧もスプレッドシート最終行(前回の継手の最後のパス)の値がデフォルト表示されます。

- 完了ボタンを押すまでは、入力内容はブラウザの`localStorage`(端末内)に自動で一時保存されます。ブラウザが落ちても同じ端末・同じブラウザなら復元できますが、**別の端末には引き継げません**(1つの継手の記録は、開始から完了まで同じ端末で行ってください)。
- 電流・電圧・アークタイム(スタート/ストップの計測時間)・溶接長から、パスごとに入熱量(kJ/cm)を自動計算します。パス間温度・入熱量が管理基準値を外れると自動でNG判定されます。
- パス記録画面では、誤タップで記録中の内容が見えなくなる事故を防ぐため、ヘッダーの「← 戻る」ボタンは表示されません(ホームへは完了後の「🏠 ホームに戻る」ボタンから戻ります)。
- 「📜 履歴を検索する」から開く継手詳細画面でも、パス一覧の値の編集(再保存)・積層図の後からの追加/差し替えができます(作図・撮影が完了操作より後になった場合を想定しています)。

## 構成

```
weld-heat-management/
  index.html   … フロントエンドのHTML（画面構造のみ）
  style.css    … スタイル（iPad/スマホでの片手入力を想定した大きめUI）
  app.js       … 画面ロジック + GAS APIとの通信処理（fetchでGET/POST）
  gas/Code.gs  … GAS側に貼り付けるバックエンドコード（JSON専用API）
```

## 1. スプレッドシートの準備

以下2枚のシートを用意します。**列の並び順は自由**です(列名でマッチングするため、名前さえ合っていればどこに置いても構いません)。

### シート「入熱パス間記録」(1行=1パス)

以下の列名をすべて含めてください(1行目がヘッダー行)。

```
ID, 工事名, 検査日, 部材, サイズ(幅), 板厚, 部材サイズ, 溶接者, 検査員（入力者）,
層数, パス数, 溶接長, 電流, 電圧, スタート, エンド, アークタイム, パス間温度,
インターバル, 備考, 計測, 製品名, 材質, 溶接方法, 気温, 順序,
ルートギャップ, 開先角度, image, 積層図,
入熱上限(kJ/cm), パス間温度下限(℃), パス間温度上限(℃), 判定
```

- `ID` はパスごとに1件ずつ自動採番される連番です(空にしておいてください)。
- `判定` 列の見出しに補足説明を追記しても構いません(例:「判定(OK/NG。アプリが自動入力します)」)。アプリ側は列名の前方一致でマッチングするので、`判定`から始まっていれば問題ありません。

### シート「情報」

**A〜F列: マスタ選択肢**(列ごとに独立したリスト)。それぞれの列にあらかじめよく使う値を何行か入れておくと、アプリ側でプルダウン選択できるようになります(その場での新規追加も可能です)。

```
工事名, 溶接者, 検査員, 部材, 材質, 溶接方法
```

**I〜J列: 設定値**(キー・値のペア。1行に1項目ずつ、以下のキー名を左側(I列)に、値を右側(J列)に入力してください)。

| I列(キー) | J列(値) | 用途 |
|---|---|---|
| データソーススプシID | このスプレッドシートのID | 表示確認用(コードからは参照しません) |
| 製品名フォルダ | DriveフォルダID | 製品名タグ写真の保存先 |
| 積層図 | DriveフォルダID | 積層図写真の保存先 |
| Geminiモデル名 | 例: `gemini-3.5-flash-lite` | 製品名タグ写真のOCRに使うGeminiモデル |
| タイムゾーン | 例: `Asia/Tokyo` | 日時表示に使うタイムゾーン |
| APIKEY | Gemini APIキー | OCR呼び出し用(サーバー側のみで使用。外部に公開されません) |

### 検査員別シート(自動作成。手動で用意する必要はありません)

「情報」シートの検査員列は検査員名簿を兼ねます。アプリで検査員を初めて選ぶ/新規登録すると、その時点の「情報」シートA:F列の内容を丸ごと複製した専用シート(シート名=検査員名)が自動的に作られます。以後、工事名・部材・材質・溶接方法・溶接者の追加・削除・デフォルト設定はその検査員の専用シートの中だけで完結し、「情報」シートや他の検査員には影響しません(「情報」シートは新規検査員シートを作る際のテンプレートとしてのみ使われます)。

「製品名フォルダ」「積層図」は、Google Driveで新規フォルダを作成し、フォルダを開いたURLの `drive.google.com/drive/folders/【ここがフォルダID】` の部分を控えます。**この2つのフォルダは同じ親フォルダの中に作成してください**(PDF変換用の一時ファイルは、製品名フォルダの親フォルダに自動的に保存されます)。

Gemini APIキーは [Google AI Studio](https://aistudio.google.com/) 等で取得したキーを使用します。

## 2. GAS（バックエンドAPI）のセットアップ

このアプリのGASは、上記スプレッドシートに**コンテナバインド**(スプレッドシートに紐づく形)で作成します。`SPREADSHEET_ID` の設定は不要です(`SpreadsheetApp.getActiveSpreadsheet()` で自動的に自分自身を参照します)。

1. 上記スプレッドシートを開き、「拡張機能」→「Apps Script」で新しいGASプロジェクトを開きます。
2. `gas/Code.gs` の内容をまるごとコピーし、GASエディタの `コード.gs` に貼り付けます(SPREADSHEET_ID・DRIVE_FOLDER_IDのような書き換えは不要です)。
3. 保存後、右上の **「デプロイ」→「新しいデプロイ」** を選択します。
4. 歯車アイコンから種類を **「ウェブアプリ」** に設定し、以下を指定します。
   - **次のユーザーとして実行**: 「自分」
   - **アクセスできるユーザー**: **「全員」**（フロントエンドから匿名でアクセスするため必須）
5. 「デプロイ」をクリックし、表示される **ウェブアプリのURL**（`https://script.google.com/macros/s/xxxxx/exec` の形式）をコピーします。
6. 初回デプロイ時にGoogleアカウントの承認画面が出るので、権限（スプレッドシート・Drive・Google Docs・外部サービス(Gemini API)への接続権限）を許可してください。PDF出力機能はGoogle Docsを一時的に作成してPDF変換するため、Docsの権限も要求されます。
7. **このURLをClaudeとのチャットに貼り付けてください。** `app.js` の `GAS_API_URL` に反映してGitHubにpushします。
8. コードを修正した場合は、この新規デプロイを編集し「新バージョン」として更新すれば、URLは変わりません。

### 注意点

- 既存の「試合記録アプリ」とは**別のGASプロジェクト・別のスプレッドシート**を使います。
- 複数人が同時に記録を保存しても壊れないよう、ID採番や書き込みは`LockService`で排他制御しています。
- CORSのプリフライト回避のため、POSTは `Content-Type: text/plain` で送信しています（試合記録アプリと同じ方式）。
- レスポンスは常にHTTP 200で返り、成否は返却JSONの `status` フィールド（`success` / `error`）で判定します。
- チーム内利用を想定しており、認証トークン等は付けていません。社外に公開する場合は追加の認証を検討してください。
- `listMasterLists` はA〜F列だけを公開する実装になっており、I〜J列の設定値(APIKEY含む)は外部APIから取得できません。「情報」シートに列を追加する際は、この境界を壊さないよう注意してください。

## 3. フロントエンド（GitHub Pages）のセットアップ

1. `app.js` の先頭にある `GAS_API_URL` を、手順2で取得したウェブアプリのURLに書き換えます。
2. 変更をリポジトリにコミット・プッシュします。
3. リポジトリ直下の `index.html`（試合記録アプリ）と同様に、GitHub Pagesの `Settings → Pages` で `Deploy from a branch` / `main` / `/ (root)` を設定していれば、このフォルダも自動的に配信されます。
4. 公開後、`https://<ユーザー名>.github.io/<リポジトリ名>/weld-heat-management/` でアクセスできます。ホーム画面に追加（PWA的に）しておくと、アプリのようにワンタップで開けます。

## 4. 動作確認

1. 上記URLにアクセスし、「🔥 入熱・パス間温度管理」のホーム画面が表示されることを確認します。
2. 「＋ 新しい管理記録を開始」から継手情報を入力します。まず検査員(入力者)を選択(または新規入力)すると、その検査員専用のデフォルトで工事名・部材・材質・溶接方法・溶接者が有効化されることを確認します(検査員を確定するまでこの5項目は選択できません)。工事名・部材・製品名・サイズ(幅)・板厚・材質・溶接方法・溶接長・気温・計測・ルートギャップ・開先角度・溶接者・検査員(入力者)が必須で、すべて埋まるまで黄色背景・赤文字の点滅アラートが表示され「記録を開始する」ボタンはグレーアウトされます。「製品名(符号)」欄の横の「📷 画像」ボタンで製品名タグの写真を撮ると、自動読み取りされた文字列が「製品名」欄に入ることを確認します(読み取れない場合は手入力できることも確認)。すべて入力すると「記録を開始する」をタップできます。
3. パス記録画面で、層番号を確認し、「▶ スタート」の隣に「✅ このパスを記録」ボタンが並んでいることを確認します。電流・電圧・パス間温度を入力 → 「■ ストップ」→「✅ このパスを記録」の順に数パス記録し、一覧テーブルに行が追加されることを確認します。基準値を外れた値を入れた場合、警告表示と赤色の行になることを確認します。またこの画面ではヘッダーの「← 戻る」ボタンが表示されないことを確認します。
4. ブラウザをリロードし、ホーム画面に「▶ 前回の途中から再開する」ボタンが出て、入力途中のパスが復元されることを確認します。
5. 「⚡ 積層図を撮る」は必須ではなく、撮影しなくても「🏁 溶接完了・スプレッドシートへ記録する」ボタンが押せることを確認します。押すと総合判定（OK/NG）が表示されること、スプレッドシートの「入熱パス間記録」シートにパス数分の行が追加されていることを確認します。
6. 「📄 PDFを出力する」を押し、数秒後に端末へPDFが直接ダウンロードされること(工事名・部材・継手情報・パス一覧テーブルが正しく入っていること)を確認します。
7. 「📜 履歴を検索する」から、これまでの記録が継手単位で一覧表示され、キーワード検索（工事名・部材・製品名・氏名）で絞り込めること、タップして詳細画面を開けることを確認します。詳細画面では、パス一覧の値(層・電流・電圧・アーク・パス間温度)を編集すると入熱・判定が再計算され、「🔄 再保存する」でスプレッドシートへ反映できること、「⚡ 積層図を撮る(後から追加・差し替え)」で完了後にも積層図を追加・差し替えできること、PDF再出力できることを確認します。
8. どの画面でも上部に会社ロゴ+社名の固定ヘッダーが表示され、スクロールしても常に見えることを確認します。また、パス記録画面以外のどの画面で「← 戻る」を押しても、直前の画面ではなく必ずホーム画面に戻ることを確認します(入力途中のデータは下書きとして残ります)。
9. ホーム画面「⚙ 【検査員別】初期値設定」を開き、まず検査員を選択(または新規入力)する画面になっていることを確認します。検査員を選ぶと、工事名・部材・材質・溶接方法・溶接者の5項目がアコーディオン形式(見出しは常に全部表示、クリックした項目だけ中身が開く。1度に1項目のみ開く)で表示され、値の追加・削除・デフォルト設定ができることを確認します。別の検査員に「検査員を変更」で切り替えると、その検査員専用の別のリスト・デフォルトが表示されること(他の検査員の追加/削除/デフォルト変更が影響しないこと)、新規記録画面でその検査員を選んだ時に設定したデフォルトが自動選択されることを確認します。新規検査員を入力すると、スプレッドシートにその検査員名のシートが自動作成され、「情報」シートの検査員列にも追加されることを確認します。

## トラブルシューティング

- **一覧が読み込めない**: `GAS_API_URL` が正しいか、GASデプロイの「アクセスできるユーザー」が「全員」になっているかを確認してください。
- **PDF出力でエラーになる**: 「情報」シートI:J列の「製品名フォルダ」「積層図」のフォルダIDが正しいか、GASの初回承認でGoogle Docs/Driveへの権限を許可したかを確認してください。
- **製品名の自動読み取りが常に失敗する**: 「情報」シートI:J列の「APIKEY」「Geminiモデル名」が正しいか、GASの初回承認で外部サービスへの接続を許可したかを確認してください。読み取りに失敗しても手入力できるので運用は止まりません。
- **CORSエラーが出る**: `app.js` のPOSTの `Content-Type` が `text/plain;charset=utf-8` になっているか確認してください（`application/json` にするとプリフライトで失敗します）。
- **列が見つからないエラー**: 「入熱パス間記録」「情報」シートに、上記の列名がすべて存在するか確認してください（列の順番は自由です）。
