## レシピ

### GASのJSONを速く配る
- 効果: GAS直接22秒超 → Vercel中継API+CDNキャッシュ(数秒)(tori-robo)
- やり方: `api/data.js` でGASを取得(最大3回リトライ)、`Cache-Control: public, s-maxage=300, stale-while-revalidate=86400`。画面はlocalStorageの前回結果を即表示→裏で更新。失敗時だけGAS直接へフォールバック。
- 注意点: 関数は本番デプロイしないと動かない。raw.githackの確認URLでは関数が無くGAS直接になる。詳細は `CLAUDE.md` 該当節。
- 使ったアプリ: tori-robo

### 自動デプロイを止めたまま公開する
- 効果: push・マージのたびのデプロイ消費を0に(daily-reportで確認)
- やり方: アプリのフォルダに `vercel.json` `{ "git": { "deploymentEnabled": false } }`。公開時だけ `create_deployment`(「デプロイして」の指示があったときのみ)。
- 注意点: Ignored Build Stepは `-- .` と書く(`-- ./<フォルダ>` は常にスキップ)。teamIdは渡さない(403)。
- 使ったアプリ: daily-report, sonekibunki, cost-insight, tori-robo, app-launcher

### GitHub上での画面確認(Vercel枠を使わない)
- 効果: 確認のたびのデプロイが不要
- やり方: `https://raw.githack.com/aism24/-/<branch>/<フォルダ>/index.html`(jsDelivrはHTMLがtext/plainで返るので不可)。
- 注意点: 反映ラグあり。JS/CSSに `?v=<目印>` を付けて毎回更新し、curlで目印が一致してから案内する。
- 使ったアプリ: 全アプリ共通

### Functions Storageを増やさない(関数を持つアプリ)
- 効果: pdf-diff-appで1デプロイ約1GB → 関数1本に統合して約60MB。旧デプロイ削除で0 Bまで戻せる
- やり方: 関数を1本に統合、scipy除去、本番デプロイは1回だけ。旧本番以外のデプロイを削除。
- 注意点: 削除の反映はUTC日単位(日本時間9:00以降)。管理ライン7GB。
- 使ったアプリ: pdf-diff-app

### GASが遅いときの診断
- やり方: 実測してから対応を決める(スキル `gas-performance-diagnosis`)。「GAS自体が遅いから仕方ない」と決めつけない。

### GASの不調(404・保存エラー・取得失敗)の切り分け
- 効果: 不要なコード変更を避けられた(404の件はPRをrevertして元に戻した。#426→#427)
- やり方: 並列6リクエストを複数回curlし、echo側の404/302を確認 → Apps Scriptの「実行数」で完了か失敗かを見る。2段階応答(1段目約1秒、2段目の受取URLは1回限り・約15秒で期限切れ)が原因のことがある。保存時にエラーページが返ったら、シートを読み直して保存済みか確認する(#464)。
- 注意点: 実行ログの「実行中」は止まっているのではなく、結果が受け取られなかったもの。原因が分かる前にコードを変えない。「憶測で判断しない」(書き込み元の調査では、PCアプリと推測したが実際は無題のGASだった)。
- 使ったアプリ: daily-report, jikko-yosan(実行予算)

### GAS(Code.gs)を貼り替えたあとの確認
- やり方: 実データの読み込みと保存を実測する(読込1.5秒→2.4秒)。保存テストは同じ値を書き戻し、シートの内容を変えない。GAS改修は1つずつ小さく実装し、実機で確認する(fetchAll・不要シート除去は404の疑いで撤回済み)。
- 使ったアプリ: jikko-yosan, 生産管理ダッシュボード

### ブラウザで外に出られないときの画面確認
- やり方: curlで取った実データを流し込んで画面確認する。確認用URLはコミット指定だと先に反映され、main指定はキャッシュで遅れる。ブラウザで確認できなかったときは、正直に「未確認」と報告する。
- 使ったアプリ: jikko-yosan, sonekibunki

### 本番デプロイ後の反映確認
- やり方: 本番ファイルをfetchして版の目印(例 `?v=20260928l`)を確認する。
- 使ったアプリ: sonekibunki

### 今日のデプロイ回数を数える
- やり方: `get_team` や請求系は403。プロジェクト単位の `list_deployments` をUTC日付で数える(pdf-diff-pythonappで12回と集計できた)。
- 注意点: 連携中プロジェクトの有無は `list_projects`(repoUrl指定)が0件かで確認する。

### 古いデプロイの削除(Vercel)
- 効果: Functions Storage 約2.2GB → 0 B(本番1件だけ残した状態)
- やり方: 「現本番以外」を削除。Previewは30日で自動削除、旧本番は手動削除。反映はUTC日単位(日本時間9:00以降)なので、削除直後の数値で「減らない」と判断しない。値は時刻つきで記録する。
- 使ったアプリ: pdf-diff-app

### 引き継ぎ書の作り方
- やり方: 冒頭に「フォルダ内の最新版を読んで続きから」と書く。Googleドキュメントは書き換えられないので、後継版を同じフォルダに新規作成する。保存後に中身を読み直して確認する。引き継ぎ書が旧版と新版で2つになったら1冊に統合し、旧版はゴミ箱へ(30日は復元可)。
- 使ったアプリ: 全アプリ共通

### 取り込みが正しいかの検証(cost-insight)
- やり方: 数値を前回記録と突き合わせる(在職245人が一致)。実データはGitHubに上げない。
- 使ったアプリ: cost-insight

### pdf-diff-app: 送信量の削減
- 効果: 1ページ比較ごとにPDF全体を送っていた → 対象ページだけ切り出して送る
- 使ったアプリ: pdf-diff-app

### モデルの使い分け(質問への回答)
- 普段はSonnet、難しい作業だけOpus。

### 機能追加の検証の流れ(pdf-diff-app、9/19)
- やり方: Playwrightで操作を通して検証 → リグレッションテスト全件合格 → PR → マージ → 本番URLで確認。ロジックはPythonで直接実行し、正解データと照合してから統合する(表31/31、文章 削除6/追加8で一致)。
- 注意点: サンドボックスのブラウザがCDN不安定(ERR_TOO_MANY_RETRIES)なら、画面が呼ぶのと同じAPIを直接叩いて検証する。ロジックのJS再実装は嫌われる(「Pythonで実施だよね? ずれが生じる」)。API無しのときは501を明示し、誤った結果は出さない。
- 使ったアプリ: pdf-diff-app, tdf-master-web

### 図面読み込みの高速化(pdf-diff-app、PR #283)
- やり方: ページ単位のAPI呼び出しとpdf.js描画を各3並列化。未使用のデッドコード(clusterRows)を削除。結果と表示順は不変。本番で6ページPDFを解析して確認。

### Vercel化のつまずき4点(pdf-diff-app)
- ハイフン付きファイル名でentrypointエラー / Framework Preset自動検出 / Production Domain未割当 / プロジェクト名の衝突。引き継ぎ書に記録済み。

### GAS版(app-launcher)をVercel化したときの手順
- やり方: リポジトリを変更しただけではGAS側に反映されない。GitHubのURL案内 → Apps Scriptへ貼り替え → 再デプロイ(v29)→ 実際にfetchして確認。名前が似たVercelプロジェクト(app-launcher-three)は別物なので、fetchして確認する。
- 経緯: 「基本的に全てのGitHub経由アプリはVercelで実施。記憶して」が方針の発端。リポジトリがPrivateだと無料のGitHub Pagesが使えず、完全無料を保つためVercelに統一した。

### 複数セッションの衝突を避ける
- やり方: 同じリポジトリを複数セッションで同時に触らない。作業前にmainと未マージブランチを確認する。衝突したら、正とするブランチを決めて統合する(9/19は、Python方式のブランチを正とした)。マージ競合は手動で解消し、元と同一であることを確認してからpushする。
- 注意点: 旧セッションの「同じフォルダに保存」という指示を流用しない。保存先は `CLAUDE.md` の表に従う。

### 旧方式の注意(使わない)
- Ignored Build Stepに `-- ./<フォルダ名>` と書く方式は誤り(常にスキップされる)。`-- .` が正しい(`CLAUDE.md` 参照)。
- 「pushのたびにcompare URLを案内する」運用は、確認用URL(raw.githack)の毎回添付に置き換わった。

## ユーザーがよく出す指示(繰り返し・訂正が多いもの)
- アプリは完全無料で実装し、URLで配布する(常に最新版)。

- 「憶測で判断しない」。原因が分かる前にコードを変えない。
- 「構想の相談中は実装しない」。
- 引き継ぎ書は1冊に統合し、保存後に内容を読み直す。「新セッションごとに説明させるな」(保存先ルールは `CLAUDE.md` を読めば分かるようにする)。
