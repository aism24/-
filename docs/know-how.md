## レシピ

### GASのJSONを速く配る
- 効果: GAS直接22秒超 → Vercel中継API+CDNキャッシュ(数秒)(tori-robo)
- やり方: `api/data.js` でGASを取得(最大3回リトライ)、`Cache-Control: public, s-maxage=300, stale-while-revalidate=86400`。画面はlocalStorageの前回結果を即表示→裏で更新。失敗時だけGAS直接へフォールバック。
- 注意点: 関数は本番デプロイしないと動かない。raw.githackの確認URLでは関数が無くGAS直接になる。詳細は `CLAUDE.md` 該当節。
- 使ったアプリ: tori-robo

### 各アプリに「← アプリ一覧へ」ボタンを共通部品で付ける
- 効果: アプリごとの手書き修正 → 1ファイル+HTML1行(17アプリ。縁が光り、背景色・文字色が別リズムで変化。コントラスト比6.7以上を全コマで実測)
- やり方: 正本 `docs/to-launcher/to-launcher.js` を各アプリのフォルダにコピーし、`<script src="to-launcher.js?v=.." data-target="セレクタ" data-mode="in|before|beforePrev">` を `</body>` 前に1行。背景の明暗と他ボタンの色相(40°以上離す)を自動判定。
- 注意点: Vercelはフォルダ単位の配信なので、共通ファイルは各フォルダへコピー(正本を直したら全フォルダへ再コピー)。CRLFのHTMLはバイナリで編集する(Pythonのテキストモードだと全行が差分になる)。
- 使ったアプリ: jissun-open ほか16アプリ

### Driveの名前変更(update_file)で、個人のマイドライブ直下に混入する
- 効果: 直下に混入していた引き継ぎ書14冊 → 0冊(2026-10-19、元の会社フォルダへ戻して直下0件を確認)
- やり方: 名前を変えたら、そのファイルに `parentId`=元の会社フォルダ を指定した `update_file` を続ける。`search_files` で `parentId = 'root'` かつドキュメントを検索し、0件を確認する。
- 注意点: `create_file`+`parentId` で新規作成した分は混入しなかった。混入しても元の会社フォルダには残る(移動ではなく親の追加)。
- 使ったアプリ: 引き継ぎ書の全アプリ

### 引き継ぎ書を多数まとめて更新する(forkで3並列)
- 効果: 9冊を3つに分けて並行 → 約3.5〜7.3分で完了(逐次の所要は未計測)
- やり方: 共通の追記内容と、アプリごとのフォルダID・最新版のID・タイトルを渡し、各担当が「旧版を全文読む→新版を `create_file`(HTML、`parentId`必須)→保存先一致を確認→読み戻し」を行う。
- 注意点: 旧版は残す(タイトルの「最新版」を外すのは別の指示で)。表の列幅が少し変わることがある。誤記は削除でなく改名で残してから、ユーザーに削除可否を聞く。
- 使ったアプリ: cost-insight, tori-robo, shipping-list-link, daily-report, company-ai, tdf-dim-count, huguai, jissun-open, app-launcher

### Vercelの本番デプロイが CANCELED になる
- 効果: 4プロジェクトが作成直後に CANCELED → Ignored Build Step を「Automatic」に直して `forceNew`=1 で再デプロイ → 全件 READY(2026-10-19)
- やり方: CANCELED になったら、Settings → Build and Deployment → Ignored Build Step を確認する(コマンドが入っていると、Root Directory内で実行されるため常にスキップになりうる)。
- 注意点: Claudeからは設定の中身が読めない。直すのはユーザー。再デプロイは同じSHAでも `forceNew`=1(数値)で新しく作る。
- 使ったアプリ: jissun-master-jidokinyu, unso-check, tdf-master-web, production-management(jissun-open は 10/16 に同じ症状)

### 自動デプロイを止めたまま公開する
- 効果: push・マージのたびのデプロイ消費を0に(daily-reportで確認)
- やり方: アプリのフォルダに `vercel.json` `{ "git": { "deploymentEnabled": false } }`。公開時だけ `create_deployment`(「デプロイして」の指示があったときのみ)。
- 注意点: Ignored Build Stepは `-- .` と書く(`-- ./<フォルダ>` は常にスキップ)。teamIdは渡さない(403)。
- 使ったアプリ: daily-report, sonekibunki, cost-insight, tori-robo, app-launcher

### GASが遅いときの診断
- やり方: 実測してから対応を決める(スキル `gas-performance-diagnosis`)。「GAS自体が遅いから仕方ない」と決めつけない。

### GASの「データが少ないのに遅い」は、データ量でなく固定費を疑う(truck-fax、2026-10-28)
- 実測: 103行のシートで、1件だけ読んでも3000件読んでも2.1〜3.7秒(`ping`は1.1〜1.9秒)。シートを開いて読む固定費が1.2〜1.5秒。2本を1本にまとめても、シートの読み込みを絞っても、ほぼ変わらなかった(提案を取り下げた)
- やり方: ①ページ先頭の小さなインラインJSで、重いJSの読み込みを待たずにGETを先出し ②結果を `CacheService` に120秒置き、書き込みで世代キーを進める(読み始めの世代のキーに置くので競合しても古い内容が残らない) ③読み込み済みの全行を、ダウンロードで使い回す(60秒)
- 効果(実測、curl): init 2.3〜4.3秒(平均約3.0秒) → キャッシュ命中で0.95〜1.4秒(`ping`は約1.0秒)。listImports(3000件)も 2.1〜3.7秒 → 1.0〜1.5秒。本番を実ブラウザで開いて「データ読み込み中」が消えるまで 4.3〜5.2秒 → 中央値約2.0秒(1.8〜2.5秒、6回)
- 使ったアプリ: truck-fax

### GAS Webアプリの「Failed to fetch」(CORS error)と、失敗時の無限再取得(daily-report、10/6)
- 症状: 起動時に「データの取得に失敗しました: Failed to fetch」。GAS実行数は全件「完了」。ネットワークタブは `exec` が「302→CORS error(1秒未満)」で、失敗の分だけ実行数に `doGet` が出る(受取URLが `/exec` へGETで戻され、HTMLにCORSヘッダーが無い)。
- 原因(コードで確認): 総務建築の取得失敗→`renderR5Preview`→`computeR5Groups_`が再取得→失敗…の無限ループ(9秒で293回を再現)。実行数が勝手に増え続ける。タブを閉じると止まる。
- 対処(PR): 失敗フラグで自動再取得を止め、読み取り専用の起動時5件に再試行(最大3回)を追加。jsdom+fetch差し替えで修正前後を比較(成功時は同一、一時失敗は回復、全失敗でも有限回)。
- 注意点: Google側が受取URLを戻す理由は未特定。curlでPOSTを再現するときは `-X POST` を付けない(`-L` で405になる)。「再実行する仕組みは無い」とgrepだけで決めつけない(間接呼び出しのループを見落とした)。
- 使ったアプリ: daily-report

### GASの不調(404・保存エラー・取得失敗)の切り分け
- 効果: 不要なコード変更を避けられた(404の件はPRをrevertして元に戻した。#426→#427)
- やり方: 並列6リクエストを複数回curlし、echo側の404/302を確認 → Apps Scriptの「実行数」で完了か失敗かを見る。2段階応答(1段目約1秒、2段目の受取URLは1回限り・約15秒で期限切れ)が原因のことがある。保存時にエラーページが返ったら、シートを読み直して保存済みか確認する(#464)。
- 注意点: 実行ログの「実行中」は止まっているのではなく、結果が受け取られなかったもの。原因が分かる前にコードを変えない。「憶測で判断しない」(書き込み元の調査では、PCアプリと推測したが実際は無題のGASだった)。
- 使ったアプリ: daily-report, jikko-yosan(実行予算)

### 数字の質問はAIに計算させず、コードで集計して文章にする(社内AI 第2弾、有給・欠勤)
- 効果: Gemini呼び出し0回(無料枠を消費せず、数字の誤りも出ない)。期間・休日除外・重複除外・B5の+2000をNodeテスト34件で確認
- やり方: 質問文から「誰(私/氏名)・期間」を決定的に読み取る(`parseAbsenceQuery`)→ シートを集計 → 定型文で回答。就業規則の質問とは「本人/氏名の有無」で振り分ける。
- 注意点: Dateはタイムゾーンでずれるため、GAS側で文字(yyyy/MM/dd)に直してから純粋関数へ渡す。有給の年度は4/1、日報集計は11/21、月度は21日区切りと区切りが違うので、回答に期間を必ず書く。
- 使ったアプリ: company-ai

### 大きなシートから期間だけ素早く読む(社内AI 日報、数万行)
- やり方: 日付をyyyymmddの数値にして日付順に書き、質問時は日付の列だけ読んで二分探索 → 期間の行だけ `getRange` で読む(Date変換の `formatDate` を数万回呼ばない)。
- 注意点: 書き込みは15000行ずつ分割。横長(1行に5件)の日報は、1作業=1行の縦形式にそろえてから集計する。B5の時間は終了−開始(休憩を引かない)なので回答に注記する。
- 使ったアプリ: company-ai

### 「一般的な質問」はコードで答える(カレンダー・日付)
- やり方: 「今度の土曜」「次の連休」など相対表現をコードで日付に直し、カレンダーの出勤/休日から答える。日付の指定が無い質問(休日の定義など)は規則側へ振り分ける。
- 使ったアプリ: company-ai

### 6分制限を超える大量ファイル(約34件のマスター)の取り込み(社内AI 生産重量)
- やり方: 状態シート(ファイルID・更新日時・取込日時)で「変わったものだけ」処理し、取込が古い順に、時間予算(240秒)の範囲で進める。残りは次回(夜間トリガー or メニューの再実行)。Excelは Drive.Files.create で一時変換して読み、すぐ削除。1ファイルの失敗で全体を止めない。
- 注意点: 既存の別アプリ(生産管理)が同じマスターを読んでいる。重量の足し方(本数を掛けない)・日付(年つき)・工事番号(索引シートを正)は既存アプリと揃える。ユーザー指示「生産重量=加工完了」「日付は締め日基準」「工事番号はスプシが正」。
- 使ったアプリ: company-ai

### 取り込みキーの重複を疑う(社内AI 生産重量、鳥取7ファイルが抜けた)
- 症状: 状態シートの行数(26)が、一覧のマスター数(33)より少ない → 差の7件が、同じ「マスタNo」で上書きされていた(ms-tottori と mst に1〜7が重複)。
- 対処: キーを「ドライブ:マスタNo」にした。検証は、ユーザーが示した正解値(今月の鳥取 451.7トン)と、実ファイルをPythonで直接集計した値が一致するかで行った(一致)。
- やり方: 「件数が合わない」ときは、まず取り込み側の件数(状態シート)と元の一覧の件数を突き合わせる。実ファイルは download_file_content(結果はファイルに保存される)を openpyxl で直接集計できる。
- 圧縮: 同じ 工事・加工先・部位・加工日 を足し合わせて約1/13(39,646→3,019行)。圧縮の前後で重量・点数が一致することをテスト。
- 使ったアプリ: company-ai

### 曖昧な質問は聞き返さず、選択肢ボタンで補った完全な1問を送らせる(社内AI、10/8)

### 毎回の全件取得は「変わらない分(版付きURLで長期キャッシュ)」と「毎日変わる分」に分ける(daily-report 10/23)
- 効果: GASの応答 21.6MB・18.8〜25秒(CDNに保存なしで本番26秒)→ 毎回取る分 4.8MB・8.7〜10.2秒(本番12.6秒、起動の度に最新)+アーカイブ分は版ごとに1回だけ(CDN保存後0.2〜0.4秒・ブラウザの保存で0秒)。GASが毎回読む保存ファイル 16.9MB→2.5MB
- やり方: GASは「毎日分+アーカイブの版(元ファイルの最終更新日時)」と「アーカイブ分(版ごとに作って保存したJSON文字列をそのまま返す)」の2つ。中継APIは `kind=archive&v=版` で、版が一致したときだけ `max-age=31536000, immutable`(違えば no-store)。画面は従来と同じ形・並びに組み立て、版が食い違えば従来の一括取得へ
- 注意: Playwright は `route` を使うとブラウザのキャッシュが無効になる(キャッシュの確認は本物のHTTPサーバーで)。ブラウザも `stale-while-revalidate` に従うので、「起動の度に最新」にしたい分は no-store+`fetch(url,{cache:'no-store'})`
- 使ったアプリ: daily-report

### 利用記録が「記録された」と分かる表示を探すには、送信箇所の前後と失敗時の表示を全アプリで洗い出す(shipping-list-link 10/23)
- 効果: Vercel16アプリの記録送信11か所を点検し、画面に出るのは2アプリ3か所と特定(うち shipping-list-link の失敗時の一文を削除。新旧で送信内容・ポップアップ本文は4通りとも一致)
- やり方: クライアントの `action: 'log…'`・`logDownload(`・`sendBeacon` と、GASの「記録」シート書き込みを grep → 各呼び出しの `.catch`・`catch` で画面に文字を出していないか読む。GASの応答を「成功・失敗・通信エラー・先に閉じてから失敗」に切り替えて比べる
- 注意: テストでPDFを毎回作り直すと作成日時が入り長さが変わる(送信内容が誤って不一致に見える)→同じPDFを使い回す。デプロイするとCDNの保存が消え、中継APIの失敗(api/links の502)が表に出ることがある→デプロイ後に中継APIの200も確かめる
- 詳細(手順・grep・16アプリの状況表): `docs/know-how/usage-log-hidden-check.md`

- **GASの原本(ファイル)表示を待たせない(truck-fax、2026-10-23)**: getFile は1回3〜4秒(ping でも約1.3秒=GAS自体の往復)。GASを触らず画面側で、一覧を出したら上から10件を2並列で先読み+マウスを0.15秒止めた行を先読み+URLごとに覚える。押してから原本表示まで 約2秒→約0.05秒(先読み済みの行。模擬で実測)。描き直しのたびに先読みの範囲を広げない(上から10件に固定)。

- **スキャンFAXの向きは画像から判定する(truck-fax、2026-10-23)**: Gemini(gemini-3.5-flash-lite)に回転角を聞くと横倒し→0・逆さま→270と外れた(正解1/3)。画面側で、長い罫線が横か縦か+表の中心の上下位置+上下1/3の文字量で判定すると 40/40 正解(5枚×4方向×PDF/PNG)。PDFの保存は pdf-lib でページの /Rotate だけ変える(画質そのまま)。

- **利用記録シートの右側に別の表を置かない(tdf-dim-count、2026-10-26)**: 起動の記録が `insertRowBefore(2)` で行ごと挿入するため、同じシートのI:Kに置いた更新履歴が起動のたびに1行ずつ下へずれ、同じ起動の2回目ダウンロード(`insertRowAfter`)では間に空行も入る。更新履歴は別シート「更新履歴」A:Cに移し、GASの `doGet?action=history` で空行を飛ばして返す→アプリ側は表示のみ(行を足せばアプリ修正なしで反映)。GASのGETはブラウザのfetchで読める(`access-control-allow-origin: *`)。

- **リファクタの回帰確認は「画面+Excelの中身」を変更前後で丸ごと突き合わせる(tdf-dim-count、2026-10-26)**: 変更前のmainを `git archive` で取り出し、Playwright(file://で開き、GASへの通信は `page.route` で偽の応答)で全操作(TDF4件×まとめ幅4種+②+リセット)の `#out` のHTML・ボタンの状態・ダウンロードしたExcelの全シート(XLSX.readで読む)・ファイル名・送信した記録を保存→変更後と比較。65場面すべて一致を確認してからマージした。GASはシートのモック(配列+行に付く目印)で同じ操作列を流して比較。
- **ダウンロード時にしか使わないCDNライブラリは `defer` にする(tdf-dim-count、2026-10-26)**: body末尾の通常の `<script>` だと、ライブラリの取得が終わるまで app.js が動かない。xlsx.full.min.js(約900KB)を4秒遅らせた模擬で、起動画面のボタンが押せるまで 4425ms→48ms。使う側は従来どおり `typeof XLSX === 'undefined'` なら警告。
- **raw.githack はブラウザ(Playwright含む)で開くと案内画面が出る(2026-10-26)**: curl では本物のHTML(text/html)が返るが、Chromiumで開くと「External Content Notice | rawgit.hack」の画面になり、アプリの要素が見つからずテストが30秒で失敗した。自動の挙動確認は `git archive origin/main <フォルダ>` で取り出して file:// で開く(GASは `page.route` で偽の応答)。raw.githack はユーザーが目で見る用だけにする。

- **利用記録に「起動」の行を足し、ダウンロードを同じ起動の行へ書く(tori-robo、2026-10-26)**: 記録がダウンロード時だけだと、開いただけの利用が分からなかった。起動時に `logStart`(2行目へ挿入、A=起動日時。GASが返した日時をクライアントが持つ)、ダウンロード時は `logDownload` が `start=` でA列が一致する行のB:Cを上書き(他の人の起動が間に入っても自分の行に入る。一致なし・目印なしは2行目/新規行)。起動の記録なし→起動ごとに1行。シートのモックで4ケース(2人起動・同じ起動で2回DL・目印なし・不明な目印)が想定どおり。
- 注意: GASの変更は貼り替え+新バージョンのデプロイが要るので、`CODE_VERSION`+`?action=ping` を入れておくと反映を1回のcurlで確認できる(tori-robo は 2026-10-26-log-start)。画面に「記録した」と出さない・失敗は無視する(huguai と同じ)。

- **シートに「対応づけ」の列が無い変更前→変更後は、点数で1対1に組み合わせて表示する(truck-fax、2026-10-27)**: 実データ100行(変更前7・変更後7)の確認で、行先4・車番3・氏名2・車種1・卸日1の点数(3点未満は組まない)により7組すべて正しく組めた。
- 効果: 変更前だけが上にまとまって対応が分からない → 変更前の真下に変更後が並び、変わった項目に⤵。
- 注意: テストは公開GASの `listImports` の実データで確認し、データはリポジトリに置かない(個人情報)。


- **画面最下行のホバーパネルがちらつく(マウスを動かさないのに出たり消えたり)→ 下余白でページ高を固定(app-launcher、2026-10-27)**: 最下行のパネルが下へ伸びてページが高くなり、ブラウザが自動スクロール→ボタンがマウスから外れる→パネルが消えてスクロールが戻る、の繰り返しだった。`html{scrollbar-gutter:stable;overflow-anchor:none}` と `body{padding-bottom:320px}` で、ホバー前後のページ高が858→941(変動)から1178→1178(固定)になり、入切が `in,out,in` から `in` のみになった(PR #954)。
- 注意: スクロールバー幅の対策(gutter)だけでは直らなかった(1回目の見立て違い)。原因は、画面録画(mp4)を ffmpeg でコマに分け、`signalstats` の明るさの跳ねたコマだけ見て、ページが上へずれていることで判明した。ユーザーに録画をもらうのが早い。
