# 日報全期間集計：GitHub Pages版

「日報集計アプリ」（GASコンテナーバウンド、既存のWebアプリ名は「日報アプリより集計」）の
**新しい窓口**として、GitHub Pagesで配信するフロントエンドを追加したものです。

## 既存アプリとの関係(最重要)

**既存のGAS Webアプリ（`_gas/Index.html`、`google.script.run`方式、`DailyReport`ファイルのみ対象）
には一切変更を加えていません。** 既存のデプロイ・既存のURL・既存の挙動はそのまま残ります。

このフォルダの`gas/Code.gs`は、既存の管理用スプレッドシート（「情報」「記録」シートを持つコンテナー
バウンドのスプレッドシート）に設置されている**既存のCode.gsに、新しい関数を追記したもの**です
（ファイル末尾の「ここから下は「日報全期間集計」専用の追加分」より前は、既存のCode.gsと完全に
同一の内容です）。追記されているのは主に以下です。

- `doPost(e)`: 新規のJSON APIエントリポイント（既存の`doGet(e)`はHTMLを返す処理のまま無改変）
- 「情報」シートに登録された複数のDailyReportファイル（現行+アーカイブ）を横断して読み込み、
  重複区間を排除してマージするロジック
- アーカイブファイルのキャッシュ（最終更新日時ベース）

## 複数ファイル対応について

「情報」シートには現在、以下のようなファイルが登録されている想定です。

```
DailyReport                     … 現行。直近数か月分のみ、他と重複しない
DailyReport_DATA{年}.11.21以降  … アーカイブ。{年}/11/21〜{年+2}/11/20の2年分
```

アーカイブは年1回追加され、隣接するアーカイブ同士は1年分重複します。重複区間は**開始年が
新しい方のアーカイブ**を優先して採用します（ファイル名から年を機械的にパースして判定するため、
「情報」シートに開始日・終了日の列を追加する必要はありません）。工事・社員等のマスタ参照は、
アーカイブ側ではなく常に現行`DailyReport`ファイルのものを使います。

## 構成

```
daily-report/index.html   … フロントエンドのHTML（画面構造のみ）
daily-report/style.css    … スタイル（既存モックからそのまま流用）
daily-report/app.js       … 画面ロジック + GAS APIとの通信処理（fetchでPOST）
daily-report/gas/Code.gs  … 既存のCode.gs + 新規追加分（丸ごと貼り替え用）
```

見た目・画面構成は、デザイン検討用に別途作成されていたモック（ダミーデータ版）をそのまま
流用しています。今回、ダミーデータ部分を実データ取得（GAS API経由）に置き換えました。

## 1. GAS側のセットアップ（未実施・要手動対応）

**重要: 既存のデプロイ（今チームが使っているURL）は絶対に変更しないでください。**
新しいコードは**追加デプロイ**として発行します。

1. 管理用スプレッドシート（「日報集計アプリ」）を開き、拡張機能 → Apps Script を開きます。
2. `daily-report/gas/Code.gs` の内容を、既存の `Code.gs` の中身と**まるごと置き換えます**
   （既存部分は完全に同一の内容なので、置き換えても既存の挙動は変わりません）。
3. 保存後、右上の **「デプロイ」→「新しいデプロイ」** を選択します
   （既存デプロイの「編集」ではなく、必ず「新しいデプロイ」を選んでください）。
4. 種類を **「ウェブアプリ」** にし、以下を指定します。
   - **次のユーザーとして実行**: 「自分」（`USER_DEPLOYING`。GitHub Pagesからの匿名アクセスに
     対応するために必須。既存デプロイの「自分がアクセスしたユーザーとして実行」設定とは異なる）
   - **アクセスできるユーザー**: **「全員」**
5. 「デプロイ」をクリックし、発行された新しいウェブアプリのURL
   （`https://script.google.com/macros/s/xxxxx/exec`）をコピーします。
6. **このURLをClaudeとのチャットに貼り付けてください。** `app.js` の `GAS_API_URL`
   （現在は `PASTE_NEW_DEPLOYMENT_URL_HERE` というプレースホルダーになっています）に反映して
   GitHubにpushします。

### 注意点（既存アプリと共通）

- GASのウェブアプリはCORSプリフライト（OPTIONS）に対応していないため、`app.js`からのPOSTは
  `Content-Type: text/plain` で送信し、GAS側で`JSON.parse(e.postData.contents)`として読み取って
  います。`application/json`にするとプリフライトが発生し失敗するので変更しないでください。
- レスポンスは常にHTTP 200で返り、成否は返却JSONの`status`フィールド（`success`/`error`）で
  判定します。

## 2. フロントエンド（GitHub Pages）のセットアップ

1. 上記手順で取得した新しいデプロイURLを `daily-report/app.js` 先頭の `GAS_API_URL` に設定します。
2. `main`ブランチにマージ済みであれば、`https://aism24.github.io/-/daily-report/` で自動的に
   公開されます（このリポジトリのGitHub Pagesは`main`ブランチのrootから配信する設定のため）。

## 3. 動作確認（未実施）

GASプロジェクトへのApps Script API経由のアクセス権がAI側に無いため、上記のGAS側デプロイ作成
（手順1）はユーザー自身の手動対応が必要です。デプロイURLが判明し次第、以下を確認してください。

1. GitHub PagesのURLを開き、パスワードロック画面が表示されること。
2. パスワード（当日の日付の一の位）を入力して解除し、工場選択 → ホーム画面まで進めること。
3. ①〜④のいずれかの画面で、工事・社員等の選択肢が実データ（ダミーではない）で表示されること。
4. 期間をアーカイブ年度をまたぐ範囲に設定し、重複した日付の行が二重にカウントされていないこと。
5. Excelダウンロードボタンで実際にファイルがダウンロードされ、内容が正しいこと。

## トラブルシューティング

- **一覧や結果が読み込めない**: `GAS_API_URL`が正しいか、新規デプロイの「アクセスできる
  ユーザー」が「全員」、「次のユーザーとして実行」が「自分」になっているか確認してください。
- **CORSエラーが出る**: `app.js`のPOSTの`Content-Type`が`text/plain;charset=utf-8`になっているか
  確認してください（`application/json`にするとプリフライトで失敗します）。
- **既存のGAS Webアプリの動作がおかしくなった**: このフォルダの変更は既存の`doGet`や
  `google.script.run`関数群には一切触れていません。もし既存アプリに影響が出た場合は、Code.gs
  の貼り替え時に何か別の変更が混ざっていないか確認してください。
