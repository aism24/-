## 1. 背景・目的

Excelマスターデータ（シート名：`ﾏｽﾀｰﾃﾞｰﾀ`）で鉄骨製品を管理している。

- **F列（図番）**：各行の図面番号。セルにハイパーリンクが設定されており、リンク先は実寸法師（鉄骨CADアプリ）の図面データファイル（`.tdf`）。UNCパス例：
  `file://192.168.1.2/share/①進行中工事/26-16 カゴヤ多々羅キャンパス.../WA1-0C-01　260619.tdf`
- **G列（製品マーク）**：図面内の個別製品の識別名（例：`0C-X17Y5`）
- **X列（加工）**：加工日。日付が入っていれば加工済み、`*` なら未加工

**やりたいこと**：X列に加工日が入力された製品について、F列のハイパーリンク先である実寸法師の図面ファイルを開き、その図面上に「加工日」情報を書き込んで保存する作業を自動化したい。

### データの重要な特性（実データで確認済み）

- 全114行に対し、F列（図番）のユニーク値は44種類 → **1つの.tdfファイルに複数の製品マーク（行）が紐づくケースが大半**（例：`WA1-1B-02`は12製品分）
- つまり1図面＝複数製品＝複数の異なる加工日があり得る
- **【2026-09-08訂正】**上記「114行・44図番」は当時ローカルにあった一部抜粋コピーの統計だった。**社内サーバーの実マスタ全体を対象にした実際の値は820行・267図番**（うち製品マーク空欄・ハイパーリンク無しの行を除外済み、詳細は8章参照）。想定より処理規模が大きいので留意すること

## 3. 検討した2つのアプローチ

### アプローチA：.tdfバイナリを直接書き換える（× 不採用）

実際に実験を行い、以下が判明した。

**分かったこと（構造解析メモ、参考情報）**
- ファイル先頭に `TDF` マジックバイト
- テキストラベルのレコード形式を発見：
  ```
  [pre_field: 4byte] [X座標: double] [Y座標: double] [高さ: double] [幅: double] [回転角: double]
  [pad: 4byte=0] [id_field: 4byte(自己参照)] [marker: "00 08 10 00"]
  [val1: 4byte = テキストバッファ長+8] [val2: 4byte(用途不明の参照値)]
  [テキストバッファ: null終端+4バイト境界パディング]
  [トレーリング16バイト(フラグ類)] [次レコードへのポインタ的な値]
  ```
- 文字コードはCP932（Shift-JIS）
- ファイル末尾に `AC0`〜`AC255` という固定256件の管理テーブル（色コード等）を発見
- ヘッダー部（オフセット0x90/0x94）に、この末尾テーブルの先頭アドレスを指すポインタを発見（＝ファイルは複数の独立したリスト構造を持ち、ヘッダーの先頭/末尾ポインタで管理されている）

**実験結果**
- 上記構造を模して新規テキストレコードをファイル末尾に追記 → **実寸法師でエラーなく開けたが、追記した文字は表示されなかった**
- 原因：新規レコードがどの描画対象リストにも接続されていないため。レコード同士のリンク（`pre_field`／`val2`等）の正確な意味・正しい繋ぎ方が、1ファイルの解析だけでは特定できなかった
- これ以上の追い込みは「一見動いても他のデータを壊すリスク」があり見合わないと判断 → **このアプローチは断念**

### アプローチB：UI自動操作（○ 採用）

実寸法師の画面スクリーンショットで実際の操作を確認済み。

**確認できた操作フロー（1製品あたり）**
1. 実寸法師で対象 `.tdf` ファイルを開く
2. 右パネルで「文字」→「通常」を選択（機能0の一覧から。機能1=通常/枠内/バルーン/連結/引出/一覧、機能2=通常/引出/2点、機能3=通常/複数行）
3. 画面下部の文字列入力ボックスに文字列（例：`0C-X17Y5_8/27加工済`）を入力してOK（Enterキーでも右の「OK」ボタンクリックでも同じ動作）
4. 「表示位置を指定してください」の入力欄に**座標値を直接キーボード入力できる**（例：`0,0` → Enter）。マウスクリックでのピクセル位置特定は不要 ← **これが自動化の最大の難所を解消する重要発見**
5. 保存（上書き保存 or 名前を付けて保存）

**メニュー構造（ファイルメニュー、Altニーモニック対応）**
```
ファイル(F)
├ 新規作成(N)
├ テンプレートで新規作成(L)...
├ 開く(O)...
├ 閉じる(C)
├ 最近使ったファイル(D)
├ 上書き保存(S)
├ 名前を付けて保存(A)...
├ ファイル名変更(M)...
├ 読み込み(R)... / 書き出し(W)... / 追加読み込み(G)... / 抽出書き出し(T)... / 図面枠読み込み(F)...
├ 印刷(P)... / 部分印刷(E)...
├ 送信(D)...
├ 実寸法師の設定(I)...
├ 実寸法師の一時終了(U)
└ 実寸法師の終了(X)  Alt+F4
```
→ Alt+F,O（開く）、Alt+F,S（上書き保存）、Alt+F,A（名前を付けて保存）等、**キーボード操作（メニューニーモニック）で駆動できる可能性が高い**

### 状態管理の設計変更（2026-09-04）：「前回実行日時」比較→行単位JSON比較

**問題点**：当初案「前回実行日時より新しい加工日（X列）を持つ図番だけ処理」には見落としがあった。X列（加工日）は「実際に加工した日付」であり「Excelに入力した日時」ではないため、後日まとめて過去日付を入力する運用（バックフィル）があると、単純な日付比較では見逃してしまう（例：前回実行日=9/1、後日9/5に8/20分をまとめて入力→8/20<9/1なので「古い」と誤判定されスキップされてしまう）。

**採用する方式**：Excelファイルごとに状態JSONを持ち、**行ID（A列）単位で前回出力した値を記録**して現在値と突き合わせる。

- 状態JSONの保存場所：サーバーの`実行状態\`フォルダ（`\\192.168.3.2\share_01\⑰その他\Claude(sumi)\実寸法師で製品情報テキスト入力\実行状態\`、4.1章参照）配下に、Excelファイル名（拡張子なし）をキーにしたファイル名で保存（例：`カゴヤ多々羅_マスタのまま.json`）
- 状態JSONの構造イメージ：
  ```json
  {
    "excel_path": "（フルパス、参照用）",
    "rows": {
      "2616Y-1-": {"図番": "WA1-0C-01", "建方日": "9/4", "加工日": "8/27"},
      "...": {}
    }
  }
  ```
- 実行フロー：
  1. 指定されたExcelファイルに対応する状態JSONを探す。**あれば読み込む（①既存ファイルとの比較）／なければ空の状態として扱う（②新規作成）**
  2. Excel全行を読み、行ID（A列）ごとに現在の（建方日, 加工日）と状態JSONの記録を比較
  3. 記録と異なる（未記録＝新規行を含む）行があれば、その行が属する**図番を再処理対象**としてマーク
  4. 再処理対象の図番について、実寸法師で原本を開き直し、その図番に属する**全行**（未定含む）をゼロから配置して検証フォルダへ保存
  5. 保存成功後、その図番に属する全行の記録を状態JSONに書き込む（保存）。失敗した図番は記録を更新しない（次回また対象になる）
- メリット：「前回実行日時」という曖昧な概念が不要になり、バックフィル入力にも正しく対応でき、Excelファイルを変えても（＝別の工事でも）同じ仕組みがそのまま使い回せる

### 7.1 テキスト生成ロジック（確定・2026-09-08 姉妹プロジェクトの知見を反映し更新）

姉妹プロジェクト「実寸法師を開くアプリ」（同じExcelマスタの建方日・加工日列を扱う）の実装で、**日付セルは実日付／未入力（Excelのシリアル値0付近。openpyxlでは年≤1900のdatetimeや`datetime.time(0,0)`として読めることがある）／文字列（`*`等）の3パターンが実データに混在する**ことが判明済み。当初想定していた「None or `*` 文字列」の2パターンだけでは不十分なため、下記の通り防御的に修正する。

```python
import datetime

def format_date_or_mitei(value):
    if isinstance(value, datetime.datetime):
        if value.year <= 1900:
            return "未定"  # Excelのシリアル値0付近＝未入力扱い
        return f"{value.month}/{value.day}"
    if isinstance(value, datetime.time):
        return "未定"  # ごく稀にtime型として読まれるケースあり
    return "未定"  # None・空欄・"*" 等の文字列はすべて未定扱い

def build_text(mark, tatekata, kakou):
    return f"{mark}＿建方日：{format_date_or_mitei(tatekata)}＿加工日：{format_date_or_mitei(kakou)}"
```
実データでテスト済み（例：`0C-X17Y5＿建方日：9/4＿加工日：8/27`、`1G-Y5X17＿建方日：未定＿加工日：未定`）。年≤1900・time型の分岐は姉妹プロジェクトの知見からの取り込みで、本プロジェクトではまだ実データでの遭遇は未確認（念のための防御コード）。

**（2026-09-08実装・確定）**：4.2章の設計変更に沿って、上記は「建方日・加工日固定」ではなく**選択された列を可変で連結する**形に一般化して実装済み（`text_builder.py`）。

```python
NUMERIC_UNIT_SUFFIX = {"長さ": "m", "重量": "t"}  # 浮動小数点ノイズ除去＋単位付与

def format_value_or_mitei(key, value):
    if key in DATE_COLUMNS:
        return format_date_or_mitei(value)
    if value is None:
        return "未定"
    if key in NUMERIC_UNIT_SUFFIX and isinstance(value, (int, float)):
        rounded = round(float(value), 2)
        num_text = str(int(rounded)) if rounded == int(rounded) else f"{rounded:.2f}"
        return f"{num_text}{NUMERIC_UNIT_SUFFIX[key]}"
    text = str(value).strip()
    if not text or text == "*":
        return "未定"
    if isinstance(value, float) and value == int(value):
        return str(int(value))
    return text

def build_line_text(product_mark, values, selected_columns):
    """1製品ぶんのテキストを組み立てる:「製品マーク＿ラベル：値＿ラベル：値…」。"""
    parts = [product_mark]
    for key in selected_columns:
        parts.append(f"{key}：{format_value_or_mitei(key, values.get(key))}")
    return "＿".join(parts)
```
非日付列（ブロック・長さ・重量等）が空欄の場合も「未定」表示、長さ・重量は小数第2位丸め＋単位付与で確定（4.2章「確定（2026-09-08 実装セッションで決定）」参照）。この`build_line_text`の出力そのものが、11章で説明する「差分検出（テキスト完全一致判定）」の比較対象になる。

### 7.2 ハイパーリンク→UNCパス変換（2026-09-08 姉妹プロジェクトの知見を反映し更新）

姉妹プロジェクトの実装で、**xlsxハイパーリンクの表記ゆれが実データに混在する**ことが判明済み：①`file://host/share/...`（スラッシュ区切り、これまで本プロジェクトで遭遇していたパターン）、②`file:///\\host\share\...`（バックスラッシュ混じり）の2パターン。本プロジェクトでは①しか実機確認していないが、同じExcelマスタ由来のため②も混在している可能性があり、両対応にしておく。

```python
from urllib.parse import unquote, urlparse

def hyperlink_to_unc(url):
    if url is None:
        return None
    s = unquote(url)
    if "\\\\" in s:
        # パターン②: file:///\\host\share\... のようにバックスラッシュがそのまま埋め込まれている
        return s[s.find("\\\\"):]
    # パターン①: file://host/share/...%20.../WA1-0C-01　260619.tdf
    parsed = urlparse(url)
    return "\\\\" + unquote(parsed.netloc + parsed.path).replace("/", "\\")
```

- `runner.run_drawings`・`process_drawing`のシグネチャに`save_dir`引数を追加。`main.py`（CLI版）にも`--save-dir`オプションを追加（省略時は従来の`VERIFY_DIR`を使用、後方互換）

**ハマったバグと修正（2026-09-09実機テストで発見、複数段階の調査を経て解決）**：

保存先フォルダ選択で「別のフォルダを選ぶ」を押すと標準フォルダ選択ダイアログが黒画面のまま応答不能になる不具合が発生。調査の結果、以下が判明・対応した。

1. **第1段階**：`askdirectory`の`initialdir`にネットワーク(UNC)パスを渡すと固まると疑い、`initialdir`を一切指定しない2段階方式（①「このフォルダを使う/別のフォルダを選ぶ」の自作確認画面→②標準ダイアログ）に変更。しかし症状は変わらず
2. **第2段階**：同一プロセス内で複数の`tk.Tk()`を作成・破棄した後にダイアログを呼ぶのが原因と推測し、ダイアログ表示だけを完全に新しい子プロセス（自分自身を`--pick-folder`引数で再実行）に切り出す方式に変更。しかし症状は変わらず
3. **原因特定**：実機でウィンドウの状態をWinAPI(`EnumWindows`/`IsWindowVisible`)で直接調査したところ、固まっていたウィンドウは**タイトルが固定の「フォルダーの参照」（旧スタイルのダイアログ）で`visible=False`（非表示）**という状態だった。診断用の単独スクリプトでは新スタイルの「Explorer形式」ダイアログ（タイトルも指定通り表示される）が正常に開けていたことと対比すると、**新スタイルのダイアログ（`BIF_NEWDIALOGSTYLE`）はSHBrowseForFolder呼び出し前に`OleInitialize`(COM初期化)が必要**というMicrosoftの仕様に行き着いた
4. **診断**：`--pick-folder`子プロセスのメインスレッドで`OleInitialize`を呼ぶと戻り値`-2147417850`(`0x80010106` = `RPC_E_CHANGED_MODE`)で失敗することが判明。つまりメインスレッドでは既にCOMが別のモード(おそらくMTA)で初期化済みで、STAへ変更できない状態だった
5. **最終修正**：`_pick_folder_entrypoint()`内で、**COM未初期化の新しいスレッド**を1つ作り、そのスレッド内で`OleInitialize`(STA)→`tk.Tk()`→`askdirectory`を実行する方式に変更。新しいスレッドはCOM未初期化の状態から始まるため、`OleInitialize`が正常終了(戻り値0)し、ダイアログも`visible=True`・指定タイトル通りに正常表示されることを実機(WinAPI直接確認)で検証済み

この一連の調査は、PowerShellから`EnumWindows`/`GetWindowThreadProcessId`/`IsWindowVisible`をp/invokeで直接呼び出し、対象プロセスのウィンドウ一覧・可視性を確認する手法で進めた（画面を目視する以外に、ウィンドウが本当に存在するか・表示されているかをコードで確認できる）。**2026-09-09、ユーザーの実機テストで正常動作(フォルダ選択ダイアログの表示・選択とも)を確認済み。**

## 11. 差分検出の再設計：「テキスト完全一致」判定への変更（2026-09-08）

### 11.1 きっかけ

ユーザーから「一度実行したものについて、テキスト抽出内容（条件も含む）が完全一致の場合は『新しく開いて保存する必要が無い』ので無視したい。何か記録は取ってる？」と質問があった。確認したところ、**当時の実装は建方日・加工日の2列しか記録・比較していなかった**（状態管理の設計変更、174行目付近の当初設計のまま）。これには以下の抜け穴があった。

1. 建方日・加工日以外の選択列（ブロック・長さ・重量等）が変わっても検知できない
2. 列選択（条件）自体を変えても検知できない（同じ建方日・加工日なら、列構成を変えても再処理されない）

### 11.2 変更内容

- `state_manager.find_dirty_drawings(sheet, state, selected_columns)`：シグネチャに`selected_columns`を追加。行ごとに`build_line_text()`で実際に配置するテキストを組み立て、状態JSONに記録された`text`と完全一致するかで dirty 判定する（以前は`建方`/`加工`の2フィールドだけを比較していた）
- `state_manager.record_success()`：記録内容を`{"建方":.., "加工":..}`から`{"text": build_line_textの出力}`に変更
- 状態JSONの構造（新）：
  ```json
  {
    "excel_path": "（フルパス、参照用）",
    "selected_columns": ["建方", "ブロック", "長さ", "重量", "加工"],
    "rows": {
      "2616Y-1-": {"図番": "WA1-0C-01", "text": "0C-X17Y5＿建方：9/4＿ブロック：A＿..."},
      "...": {}
    }
  }
  ```
- **図番単位のグルーピングは維持**：1図番の中の一部の行だけが変化した場合でも、その図番に属する全行が再処理対象になる（従来通り）。これは「原本を毎回ゼロから開き直して配置」という設計上、変化した行だけを配置すると未変化の行の情報が出力ファイルから欠落してしまうため、意図的に維持している
- **列選択→差分検出の順序変更**：差分検出に列選択の内容が必要になったため、`app.py`・`main.py`とも「列選択」を「差分検出」より前に行う順序に変更した（9.1章参照）

### 11.3 効果

- ①建方日・加工日以外の選択列が変わった場合も正しく検知できるようになった（以前の抜け穴を修正）
- ②列選択（条件）自体を変えた場合も正しく検知できるようになった（以前の抜け穴を修正）
- ③内容が完全一致なら図番ごと再処理をスキップできるようになった（ユーザー要望どおり）

ロジックは単体テストで検証済み（完全一致→スキップ、非建方/加工列の変化→検知、列選択変更のみ→検知、図番単位グルーピング維持、の4パターンで確認）。

### 11.4 既存データの移行

既存の状態JSON（カゴヤ多々羅6行/3図番、堺データセンター153MW（後期）50行/20図番）は、上記変更を適用すると次回実行時に「変更あり」として再検出される（古い記録に新しい比較用の`text`項目が無いため）。実害はない（検証フォルダへの再保存だけで原本には触れない）が、ユーザー判断で**移行せず両ファイルとも削除**し、実行状態フォルダを空の状態からリスタートすることにした（併せて検証フォルダの出力も削除済み）。

## 12. 「完了後にフォルダが開かない」不具合の調査・修正（2026-09-09）

ユーザー報告：「全て完了したら保存先フォルダをエクスプローラーで開く」はずが、実寸法師が閉じるだけでフォルダが開かない。

### 12.1 第1段階の調査：`_pick_folder_entrypoint`の消し忘れデバッグ行

コードレビューの結果、`app.py`の`_pick_folder_entrypoint()`（「別のフォルダを選ぶ」用の子プロセス）末尾に消し忘れのデバッグ行`log("print完了、終了します")`があり、`log`がこのスコープに存在しないためNameErrorで毎回子プロセスが例外終了していたことが判明。ただし`print()`は例外より前に実行されるため、フォルダ選択結果の受け渡し自体には影響していなかった（この行を削除）。念のためソース一式を再ビルド・再配置したが、**この時点ではユーザー報告の不具合は再現したまま**だった。

### 12.2 第2段階の調査：`os.startfile`が例外を出さずに黙って失敗する

修正後も実機再テストで再現（成功1件/失敗0件なのにフォルダが開かない＝`record_success`の例外説は否定された）。`os.startfile()`（ShellExecute経由）がこの環境では**例外を出さずに黙って開かないことがある**という仮説に至った（9.6章のCOM初期化問題と同系統の疑い）。

**解決**：`finish()`内の`os.startfile(save_dir)`を`subprocess.Popen(["explorer", save_dir])`（explorer.exeを別プロセスとして起動する方式）に変更し、成功/失敗をログにも表示するようにした。実機再テストで正常にフォルダが開くことを確認済み（「OKフォルダが開けました」）。

**教訓**：GUI自動化アプリで保存後にエクスプローラー等の外部プロセスを起動する際は、`os.startfile`より`subprocess.Popen(["explorer", path])`の方が確実（[[reference_windows_gui_freeze_debugging]]と同系統の知見）。

## 13. 起動速度の最適化（2026-09-09）

ユーザー報告：「アプリを起動したときに、Excelファイル選択（リスト一覧）までが時間が長い」＋「全コードのデッドコード・矛盾・無駄なループを見直してほしい」。

### 13.1 実測→ボトルネック特定

素のPythonでapp.py起動時のトップレベルimportを計測したところ、起動〜Excelファイル選択画面が出るまでの合計約1.12秒のうち、約0.9秒を`openpyxl`（約0.6秒）と`pywinauto`（約0.3秒）のimportが占めていた。どちらも実際に使うのはもっと後の段階（Excel読み込み・実寸法師の自動操作時）なのに、起動直後に前倒しでimportされていたことが原因。

### 13.2 修正内容

- `excel_reader.py`の`import openpyxl`を`read_master_sheet()`関数内のローカルimportに変更（実際にExcelを読み込む段になるまで遅延）
- `jissun_automation.py`の`from pywinauto import ...`系を、実際に使う関数（`open_drawing`/`_find_dialog_by_class`）内のローカルimportに変更。`from __future__ import annotations`により型ヒントでの参照は実行時に評価されないため安全
- 修正後、同じ計測で起動画面までが**約0.33秒**に短縮（約3.4倍高速化）。pywinauto/openpyxlともにその時点でsys.modulesに存在しないことも確認済み
- exeは自己解凍のオーバーヘッドが別途乗るが、そちらは今回のコード変更の対象外（PyInstaller onefile方式自体の制約）

### 13.3 ついでに見つけた無駄：Excelの二重読み込み

`excel_reader.read_master_sheet`が同じExcelファイルを`read_only=True`と`read_only=False`で**2回読み込んでいた**（ハイパーリンク取得のためだけに2回目を開いていた）。`read_only=False`のみで値・ハイパーリンクとも取得できるため、1回の読み込みに統合した。ネットワーク越しの二重読み込みが無くなり、大きいマスタ（LP京都=11360行等）ほど効果が大きい。

### 13.4 リグレッション検証

実際のマスタ6ファイル全て（ITM/LP京都/カゴヤ多々羅/ランドポート京都伏見/堺データセンター153MW(後期)/堺データセンター153ＭＷ、行数111〜11360）に対し、旧実装（2回読み込み版）と新実装を並行実行し、抽出データ（columns・全行のrow_id/drawing_no/drawing_unc/product_mark/values）が完全一致することを確認（6/6一致）。全ソースのpy_compileも通過。遅延importにした関数も実際に呼び出してImportErrorが出ないことを確認済み。他ファイル（state_manager.py/runner.py/main.py/column_selector.py/text_builder.py）は目視レビューの結果、デッドコードや無駄なループは見つからなかった。

| `jissun://`独自プロトコルのURLをapp-launcherに直接2行追加 | 姉妹プロジェクト「実寸法師を開くアプリ」（`製品名より実寸を開く`フォルダ）で確立済みの、対象PCに登録済みのプロトコルハンドラーを使う方式。ユーザーが既にこの方式で**ローカル.batファイルの起動に成功したことを確認済み** | 採用（ただし①②を直接ランチャーの行にするのではなく、下記15.2の専用ミニアプリ経由にする） |

ユーザーの意向により、app-launcherの「情報」シートに①②を直接2行追加するのではなく、
**①②へ飛ぶための専用の小さなアプリ（本フォルダ）を新規に作り、ランチャーにはそのアプリの
GitHub PagesのURLを1件だけ登録する**方式を採用した。

### 15.2 実装（本フォルダに同居）

他のGAS × GitHub Pagesアプリ（`open_jissun/`・`production-management/`等）と同じ構成に
揃えた、番号付きボタン2つだけの単純なランチャーページ。

```
jissun-master-jidokinyu/
  README.md    … 本ファイル(構想サマリー + 本セクション)
  index.html   … フロントエンドのHTML(画面構造のみ)
  style.css    … スタイル(ダーク基調、①②の番号付きボタン)
  app.js       … 「情報」シートから項目を取得し、番号付き<a href>ボタンとして描画
                 + クリックログ送信(GAS APIとの通信、text/plainでPOST)
  gas/Code.gs  … GAS側バックエンド(「情報」シート読み取り専用のJSON API)
```

- ボタンは実際の`<a href="jissun://...">`タグとして実装している（JSの`location.href`代入は
  ブラウザにブロックされることがあるため、ブラウザ標準のリンク遷移に任せる方が確実、という
  姉妹プロジェクト`open_jissun`での知見を踏襲）
- 表示する項目（①②）は「情報」シートに行として持たせる方式（コード変更なしで項目の増減・
  文言修正が可能。他アプリと同じ設計思想）

## 16. 実行ファイルの保存場所変更に伴う「ファイルが見つかりません」不具合（2026-09-10）

### 16.1 事象

ユーザーが下記2つのローカルファイルの保存場所を整理し、プロジェクトルート直下に新規サブ
フォルダ`00　X0Y0記入版`を作成してその配下へ移動した。

- `\\192.168.3.2\share_01\⑰その他\Claude(sumi)\実寸法師で製品情報テキスト入力\00　X0Y0記入版\実寸法師アプリ.exe`
- `\\192.168.3.2\share_01\⑰その他\Claude(sumi)\実寸法師で製品情報テキスト入力\00　X0Y0記入版\実寸法師インストール確認.bat`

この結果、本ミニアプリの①②ボタンを押しても「ファイルが見つかりません」となる不具合が
発生した。

### 16.2 原因

本フォルダのコード（`app.js`・`gas/Code.gs`）にはファイルパスは一切含まれていない。①②の
実際の`jissun://`URLは、GASがコンテナバインドされているスプレッドシート
「実寸へマスタ情報追加作業（自動）」の1枚目シート（ボタン一覧、B列URL）に直接書かれており、
`getItems()`はその値をそのまま返すだけの設計（2章・15.2章参照）。このURL文字列自体に旧フォル
ダ構成のパスが埋め込まれているため、ファイルを新フォルダへ移動しただけではURLは自動更新され
ず、`jissun://`ハンドラーがもう存在しない旧パスを探しに行ってしまっていた。

記録シート側には2026-09-10 15:12〜16:49に複数回の①②クリックが記録されており、ボタン押下
自体・GAS APIの往復（`getItems`・`logOpen`）は正常に機能していることを確認済み。問題は
ハンドラーに渡されるURLの中身（パス）のみである。

### 16.3 対応

- コード側の修正は不要（そもそもパスをコードで扱っていないため）。
- 対応が必要なのは**スプレッドシート「実寸へマスタ情報追加作業（自動）」の「ボタン一覧」
  シート（1枚目）のURL列**のみ。新フォルダを反映した以下のURLに手動で更新する必要がある
  （15.3章の表も本更新にあわせて修正済み）。

  | ボタン | 新しいURL |
  |---|---|
  | ① 実寸法師インストール確認.bat | `jissun://192.168.3.2/share_01/%E2%91%B0%E3%81%9D%E3%81%AE%E4%BB%96/Claude%28sumi%29/%E5%AE%9F%E5%AF%B8%E6%B3%95%E5%B8%AB%E3%81%A7%E8%A3%BD%E5%93%81%E6%83%85%E5%A0%B1%E3%83%86%E3%82%AD%E3%82%B9%E3%83%88%E5%85%A5%E5%8A%9B/00%E3%80%80X0Y0%E8%A8%98%E5%85%A5%E7%89%88/%E5%AE%9F%E5%AF%B8%E6%B3%95%E5%B8%AB%E3%82%A4%E3%83%B3%E3%82%B9%E3%83%88%E3%83%BC%E3%83%AB%E7%A2%BA%E8%AA%8D.bat` |
  | ② 実寸法師アプリ.exe | `jissun://192.168.3.2/share_01/%E2%91%B0%E3%81%9D%E3%81%AE%E4%BB%96/Claude%28sumi%29/%E5%AE%9F%E5%AF%B8%E6%B3%95%E5%B8%AB%E3%81%A7%E8%A3%BD%E5%93%81%E6%83%85%E5%A0%B1%E3%83%86%E3%82%AD%E3%82%B9%E3%83%88%E5%85%A5%E5%8A%9B/00%E3%80%80X0Y0%E8%A8%98%E5%85%A5%E7%89%88/%E5%AE%9F%E5%AF%B8%E6%B3%95%E5%B8%AB%E3%82%A2%E3%83%97%E3%83%AA.exe` |

- クラウド版Claude Codeセッションからは、Google Sheetsのセル書き込み手段（MCP接続）が
  無いため、このURL列の更新はユーザー側で直接スプレッドシートを開いて実施する必要がある。

### 16.4 再発防止・注意点

- 今後もこの2ファイルの保存場所を変更する場合、**必ず「実寸へマスタ情報追加作業（自動）」
  スプレッドシートのボタン一覧シートのURL列も同時に更新する**こと（コード側の変更は不要）。
- `jissun://`プロトコルハンドラー自体の実装（対象PC側でパスをどう解決しているか）は本
  リポジトリの管轄外・未確認のままである（15.3章の記載と同じ）。URL更新後も「ファイルが
  見つかりません」が解消しない場合は、ハンドラー側（ローカルPCの登録済みプロトコル
  ハンドラー）の実装も合わせて確認する必要がある。
